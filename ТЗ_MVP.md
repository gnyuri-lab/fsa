# Техническое задание на MVP веб-приложения «FSA/Анализ финансовой отчетности» 

## 1. Контекст и бизнес-проблема
Организациям необходимо проводить ежегодный финансовый анализ бухгалтерской отчетности (БО) для оценки платежеспособности, рентабельности и рисков банкротства. Процесс ручного извлечения данных из PDF, проведения расчетов в Excel и написания аналитических заключений в Word/PPTX является трудозатратным и подвержен человеческим ошибкам. 

**Проблема:** Высокие временные затраты на рутинную обработку данных и риск утечки конфиденциальной информации при подготовке внешних отчетов.

## 2. Цель и измеримые метрики
**Цель:** Создать адаптивное веб-приложение для автоматизации извлечения данных из БО, расчета финансовых показателей по заданной методологии и генерации анонимизированных отчетов.

**Измеримые метрики успеха:**
- **Время обработки:** Сокращение времени от загрузки PDF до получения готового пакета документов с нескольких часов до < 10 минут.
- **Точность:** 100% соответствие извлеченных данных цифрам в исходном PDF.
- **Безопасность:** 0 упоминаний персональных данных (ИНН, Название, ФИО) в выходных файлах.
- **Полнота:** Наличие всех расчетов, предусмотренных методологией анализа.

## 3. Пользователи и роли
| Роль | Описание | Цель |
| :--- | :--- | :--- |
| **Аналитик** | Основной пользователь приложения. | Загрузить данные, проверить их корректность, запустить расчеты и выгрузить отчеты. |
| **Руководитель** | Конечный потребитель результатов. | Получить краткую презентацию и итоговое заключение для принятия решений. |

## 4. Границы системы (Scope)

### In Scope (Входит в MVP)
- Загрузка и парсинг PDF-файлов бухгалтерской отчетности.
- Интерактивная таблица верификации извлеченных данных.
- Расчет финансового анализа по 6 разделам методологии.
- Визуализация ключевых KPI и трендов в интерфейсе.
- Автоматическая генерация файлов: `explonation.xlsx`, `rezult.docx`, `presentation.pptx`.
- Адаптивный веб-интерфейс (Desktop/Mobile).
- Механизм анонимизации выходных данных.

### Out of Scope (НЕ входит в MVP)
- Интеграция с внешними CRM или ERP системами.
- Реальная отправка документов по email или в мессенджеры.
- Облачное хранение файлов (только локальная работа в сессии).
- Система регистрации и управления пользователями (RBAC).
- Редактирование итоговых документов внутри приложения (только генерация).
- Платный хостинг.

## 5. Пользовательские сценарии

### Основной сценарий (Happy Path)
1. Аналитик открывает приложение.
2. Приложение запрашивает выбор корпоративного стиля (загрузка своего файла-шаблона или использование базового стиля приложения).
3. Приложение уточняет необходимость анализа за 3 года.
4. Аналитик загружает основной файл `БО.pdf`. Если выбран анализ за 3 года $\rightarrow$ загружает отчетность за предыдущие периоды.
5. На экране «Загрузка и проверка» подтверждает корректность извлеченных цифр.
6. Переходит на «Аналитическую панель», изучает графики и статусы рисков.
7. Нажимает кнопку «Сгенерировать пакет отчетов».
8. Скачивает анонимизированные файлы `.xlsx`, `.docx`, `.pptx`.

### Альтернативный сценарий (Ошибка данных)
1. Аналитик загружает PDF.
2. Система извлекает данные, но в одной из строк возникает ошибка распознавания.
3. Аналитик вручную правит значение в таблице верификации.
4. Система пересчитывает показатели на основе исправленного значения.
5. Аналитик продолжает по основному сценарию.

## 6. Функциональные требования

| ID | Требование | Приоритет | Описание |
| :--- | :--- | :--- | :--- |
| **FR-01** | Парсинг PDF | Must | Система должна извлекать данные из 4 форм отчетности (Баланс, ОФР, ОДДС, ОИК). Должна поддерживать как текстовые PDF, так и сканы (OCR). **Реализовано:** текстовые PDF и XLSX — точно; PDF-сканы — через OCR (Tesseract, pywik lang=rus, psm 6, растеризация 600 dpi) с выводом всех строк на экран верификации: распознавание может содержать цифровые погрешности (курсивный шрифт), аналитик подтверждает/исправляет значения перед расчетом. |
| **FR-02** | Верификация данных | Must | Интерфейс должен позволять пользователю редактировать извлеченные значения перед расчетом. |
| **FR-03** | Расчет показателей | Must | Система должна рассчитывать все KPI из `Methodology of analysis.md` (Ликвидность, Рентабельность и т.д.). **Реализовано:** обязательны две правильно заполненные и проверенные формы (Баланс, ОФР); отсутствие или ошибки необязательных ОДДС/ОИК не блокируют расчет — показатели таких форм «требует уточнения», форму можно исключить/вернуть кнопкой на экране сверки. |
| **FR-04** | Анализ банкротства | Must | Расчет Z-счета Альтмана и модели Таффлера с определением зоны риска. |
| **FR-05** | Визуализация | Should | Отображение основных KPI в виде карточек и графиков трендов. |
| **FR-06** | Генерация Excel | Must | Создание файла с листами «Исходные данные», «Расчеты» (с формулами текстом), «Диаграммы». |
| **FR-07** | Генерация Word | Must | Создание заключения по структуре `reference/brief_rezult.pdf`. |
| **FR-08** | Генерация PPTX | Must | Создание презентации с выводами и графиками. |
| **FR-09** | Анонимизация | Must | Автоматическое удаление названий компаний, ИНН, ФИО и должностей из всех выходных файлов. |
| **FR-10** | Адаптивность | Must | Интерфейс должен корректно отображаться при ширине экрана $\ge 360$px. |
| **FR-11** | Управление стилем | Should | Возможность загрузки пользовательского корпоративного стиля или выбор базового стиля приложения. |
| **FR-12** | Многолетний анализ | Should | Поддержка анализа за 3 года с возможностью загрузки отчетности за предыдущие периоды. **Реализовано:** годы определяются автоматически из колонок загруженных форм (Баланс — до 3 дат, ОФР/ОДДС — 2 года); загруженные годы включаются в расчет и диаграммы; отсутствующие годы — «требует уточнения». Отдельный экран выбора «анализ за 2 или 3 года» не реализован (Should, перенос в бэклог). |

## 8. Бизнес-правила (BR)

- **BR-01 (Квалификация риска):** Статус показателя определяется сравнением рассчитанного значения с «Рекомендуемым диапазоном» из методологии. Если значение вне диапазона $\rightarrow$ статус «Риск».
- **BR-02 (Приоритет данных):** При расчетах используются данные, подтвержденные пользователем на экране верификации. Если данные отсутствуют $\rightarrow$ результат «требует уточнения».
- **BR-03 (Анонимизация):** Любая строка, содержащая паттерны ИНН (10 или 12 цифр) или ключевые слова «ООО», «АО», «ФИО», «Должность», должна быть заменена на «[ДАННЫЕ УДАЛЕНЫ]».
- **BR-04 (Горизонтальный анализ):** Расчет динамики производится как $\frac{\text{Текущий период} - \text{Предыдущий}}{\text{Предыдущий}} \times 100\%$. Если пользователь выбрал анализ за 3 года, расчет производится последовательно для каждой пары лет.
- **BR-05 (Корпоративный стиль):** Если загружен пользовательский шаблон стиля $\rightarrow$ приложение использует его цвета и шрифты. В противном случае используется базовый стиль системы.

## 10. Технологический стек и структура проекта

### 10.1 Стек разработки
- **Язык:** Python 3.11+
- **UI-фреймворк:** Streamlit (адаптивный веб-интерфейс)
- **Обработка данных:** Pandas, Openpyxl
- **Парсинг PDF:** pdfplumber (текст), Tesseract/pytesseract (OCR для сканов; растеризация pypdfium2, детекция сетки таблицы opencv-headless)
- **Генерация документов:** python-docx, python-pptx
- **Среда исполнения:** Локальный браузер (Localhost)

### 10.2 Локальное развертывание и запуск
1. **Установка зависимостей:** `pip install -r requirements.txt`
2. **Запуск приложения:** `streamlit run src/app.py`
3. **Доступ:** `http://localhost:8501`

## 12. Ограничения, допущения и риски

### Ограничения
- Только локальный запуск (без сервера).
- Нет внешней интеграции с API.

### Допущения
- PDF-файлы имеют текстовый слой (не являются просто набором картинок/сканов).
- Данные предоставляются в стандартных формах бухгалтерской отчетности РФ.

### Риски
- **Риск парсинга:** Разная верстка PDF может привести к смещению колонок $\rightarrow$ Решение: внедрение экрана ручной верификации (FR-02).
- **Риск OCR:** Исходные файлы могут быть сканами (изображениями) $\rightarrow$ Решение: использование библиотеки OCR (например, Tesseract) для распознавания текста.
- **Риск анонимизации:** Некоторые персональные данные могут быть замаскированы $\rightarrow$ Решение: использование регулярных выражений и стоп-листа ключевых слов (BR-03).

## 13. План пилотной проверки
1. **Тест-кейс 1 (Позитивный):** Загрузка эталонного `БО.pdf` $\rightarrow$ Сверка расчетов с ручным расчетом $\rightarrow$ Проверка анонимности.
2. **Тест-кейс 2 (Негативный):** Загрузка PDF с пропущенными данными $\rightarrow$ Проверка появления меток «требует уточнения».
3. **Тест-кейс 3 (UI):** Открытие приложения в Chrome DevTools в режиме iPhone SE (375px) $\rightarrow$ Проверка доступности кнопок генерации.
4. **Тест-кейс 4 (Безопасность):** Поиск по строке «ООО» и «ИНН» в сгенерированных файлах.
